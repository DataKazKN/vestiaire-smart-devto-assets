The real questions are resale questions

A standard ecommerce scraper usually answers:

  • What is the title?
  • What is the price?
  • What is the image?
  • What is the product URL?

For Vestiaire Collective, that is not enough.

A reseller, marketplace analyst, or automation builder usually needs to answer more specific questions:

  • Which Chanel Classic Flap listings are priced below similar public listings?
  • Which seller countries return the best supply for a model?
  • Which listings are already sold?
  • Which items disappeared after repeated tracking runs?
  • Which sellers keep posting very similar listings?
  • Which market pages expose duplicate records?

That changes the scraper design.

The output has to be normalized around listing ID, seller country, condition, status, price history, and duplicate signals. Otherwise the dataset is just a product-card dump.

Market country and seller country are not the same thing

This is the first distinction to get right.

Market country is the Vestiaire locale you search. For example, France, Germany, Italy, the UK, or the US.

Seller country is the seller or item location returned in the public listing data.

If you search the French market, you can still see sellers from other countries. If your goal is sourcing only from French sellers, you need a seller country filter. If your goal is comparing how the same query behaves across markets, then market country is the right filter.

What the dataset should contain

A useful Vestiaire Collective dataset should be readable without opening the raw page again.

The important fields are:

  • Listing ID, so the same item can be deduplicated across markets.
  • Title, brand, category, and model keywords, so the query can be filtered precisely.
  • Price, currency, and price text, so exports remain readable in CSV and spreadsheets.
  • Market country and seller country, so sourcing and market comparison are not mixed together.
  • Condition, because price without condition is misleading.
  • Sold status, display status, and status source, so sold signals are not treated as perfect when they are only inferred.
  • Product URL, so the original listing can be checked manually.
  • Price history, so repeated runs can detect drops.
  • Seller summary and duplicate signals, so suspicious or repetitive public patterns can be reviewed manually.

The goal is not to make an automatic authenticity decision.

The goal is to turn public marketplace pages into structured leads for manual review, pricing analysis, and monitoring.

Example use cases

Here are the use cases the Actor is built for.

Find underpriced luxury listings:

  • Search for a specific model.
  • Filter by condition.
  • Compare prices by seller country.
  • Review likes and listing freshness.

Track sold item signals:

  • Search a model repeatedly.
  • Include public sold results when available.
  • Mark likely sold items only after repeated disappearance.
  • Keep status source visible in the output.

Benchmark seller countries:

  • Run the same query across several market countries.
  • Filter seller countries separately.
  • Compare supply, price range, and average price.

Monitor price drops:

  • Run the same tracked query on a schedule.
  • Keep a stable tracking store.
  • Compare current price against previous observations.

Flag duplicate or suspicious patterns:

  • Deduplicate by listing ID first.
  • Then review similar titles, brands, prices, and seller patterns.
  • Treat the output as a review signal, not proof.

What to watch out for

There are a few practical caveats.

Sold status is not always a single perfect field. Some signals come from public sold searches, some from sold pages, and some from repeated disappearance over time. A good scraper should expose the source of the status.

Condition can be incomplete. If the site does not return condition clearly, the scraper should not invent certainty.

Duplicate signals must stay conservative. Similar listings are worth reviewing, but they do not automatically prove anything.

Respect public data boundaries. Do not collect private account data, bypass access controls, or overload the website.
